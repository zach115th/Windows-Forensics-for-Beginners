# Chapter 11 — Review Question and Exercise Answers

*Sample answers for the Review Questions and Practical Exercises at the end of [`Chapter11.md`](../Chapter11.md). These are reference answers, not the only correct answers. Your wording will differ, and that is fine. What matters is whether your reasoning covers the same ground. For the corresponding lab, see [`Labs/Lab11/task-answers.md`](../../Labs/Lab11/task-answers.md).*

This is the capstone chapter, so the answers below draw heavily on the shipped [`Data/HR-WS17/`](../../Data/HR-WS17/) dataset. Every specific value quoted here is verifiable in that folder's CSVs. Check them rather than taking the number on faith.

## Review Questions

**1. Why is no single artifact source sufficient to resolve a case like the one in this chapter?**

Because each source answers only one part of a question that has four parts: what data, through what channel, at what time, by which account. The MFT establishes that files existed and when records changed, but says nothing about where they went or why. The registry records that a USB device was connected and that a personal cloud account was configured, but not what moved through either. Shell artifacts show which paths the user browsed, but browsing a folder is not copying from it. The OneDrive sync database shows files entering an upload queue, but only for the one channel it covers. None of them speaks to intent, and none of them covers a channel it was not built to record. An answer that survives review needs the file system, registry, shell artifacts, cloud databases, event logs, and network or SRUM data assembled into a timeline where each source constrains the others.

**2. What investigative questions should drive an exfiltration investigation, and how do they shape collection priority?**

The chapter's set is a good default. Start with existence: did the specific files exist on the host, and were they accessed in the window? Next, enumerate the plausible channels. Then ask one question per channel — USB, cloud sync, browser upload, email. Add a persistence question, asking whether this is insider activity or attacker tooling, and a cleanup question, asking whether the user tried to remove traces. The questions matter because they determine what you collect and in what order. If USB is a live hypothesis, `USBSTOR`, `MountedDevices`, `setupapi.dev.log`, shellbags, and LNK metadata move to the front of the queue. If cloud sync is live, the OneDrive `Accounts` registry key, the sync-engine database, and the client logs go first. Working question-first also prevents the failure the chapter's field note describes: building an exhaustive host timeline and discovering it cannot answer "where did the data go?" because the channel was never instrumented. The channel question drives the collection plan. The timeline supports the answer rather than generating it.

**3. How do USB-based and cloud-sync-based exfiltration channels differ in the artifacts they leave behind?**

USB leaves a device-centric trail spread across registry and shell artifacts. A `USBSTOR` enumeration entry records vendor, product, and serial number and a first-install timestamp. A `MountedDevices` entry binds the volume GUID to a drive letter. Shellbags record navigation into folders on the removable volume. LNK files have target paths that point at the device and a volume serial number that binds the shortcut to that specific physical device. What USB does *not* leave is any record of the file's content or a hash. You know the user browsed to and opened files at a path on that device, and you infer the copy. Cloud sync is the inverse: it leaves comparatively little device evidence but a rich content record. The sync-engine database carries the local path, the remote path, the file size, the sync state, the enqueue and upload-completion timestamps, and often a content hash, so you can bind a specific file to a specific upload at a specific second. The USB channel is strong on *device identity* and weak on *content*. The cloud channel is strong on *content* and weak on *where the data physically went afterward*.

**4. Why is the OneDrive settings database often the most informative single artifact for cloud-based exfiltration?**

Because it records the upload itself rather than the circumstances around it. Most artifacts in an exfiltration case are inferential. A shellbag means the user looked at a folder, a LNK means a file was opened, and an SRUM record means a process sent bytes. The sync-engine database records that a named file at a named local path was enqueued at a specific time, uploaded to a specific remote path under a specific account, and completed. In the HR-WS17 data it goes further. The `Sha256ContentHash` column carries a digest you can compare directly against the hashes legal provided in `pricing-files-known-hashes.txt`. That closes the identity question almost every other artifact leaves open. The remote path also names the account (`/personal/hr_user_personal_outlook_com/...`), separating personal from corporate sync. That combination — file identity, account identity, timing, and completion state in one row — is unusual, and it is why the database is worth prioritizing.

**5. What evidence sources can confirm or rule out a webmail-based exfiltration channel?**

Host-side, the sources start in the browser: history showing navigation to the webmail interface, cache and session data that may retain fragments, and form data or IndexedDB entries in the profile. Beyond the browser, check temporary files created by the upload flow and the Windows Search index, which sometimes preserves content fragments. SRUM or network telemetry can show outbound bytes attributable to the browser process in the same window. In the HR-WS17 data, `browser-history.csv` records navigation to `outlook.live.com` at 17:51:04 UTC, and `srum.csv` shows `msedge.exe` outbound bytes consistent with a small upload. That is enough to make webmail plausible, not enough to confirm it. What would actually confirm it lives on the provider side: Microsoft 365 or the equivalent mail-flow and audit logs showing a message sent with an attachment of a given name and size. On this channel the honest answer is usually "probable." The correct next step is a documented request for provider-side logs, not a stronger claim from host artifacts.

**6. Why is cleanup activity itself an evidentiary signal worth investigating?**

Because cleanup is a deliberate act that requires knowledge of what was done, and it frequently leaves better evidence than the activity it was meant to conceal. The USN Journal retains deletion records after the files themselves are gone, so a delete cycle is often more precisely timestamped than the create cycle. In the HR-WS17 case, the transient copies in `Temp\` were deleted at 17:55:11 UTC and the entire `C:\HR\Pricing\` directory at 17:57:42 — minutes before the user's final logoff at 18:02:14 on their last day. That sequence is not incidental housekeeping. The timing binds it to the session that also contains the USB writes and the cloud syncs. Cleanup also narrows intent in a way most artifacts cannot: removing traces implies awareness that the traces mattered. Other forms — browser history clearing visible as unexplained gaps, secure-delete tool execution in Prefetch or Amcache, event log clearing as EID 1102 or 104 — carry the same weight. A host that was sanitized shortly before an employee's departure is a finding, not an absence of one.

**7. What distinguishes a confirmed finding from a probable finding in case documentation?**

A confirmed finding is directly supported by named artifacts that record the event itself, typically from more than one independent source, with no material alternative explanation. The HR-WS17 OneDrive channel qualifies. The personal account appears in the `Accounts` registry key. The sync database records two named files enqueued and upload-completed between 17:46 and 17:49. The client logs show the corresponding upload activity, and SRUM shows `OneDrive.exe` outbound bytes in the same window. That is four artifact classes, all recording the same event. A probable finding rests on evidence that is consistent with the conclusion but requires an inferential step, and the documentation must name that step. The webmail channel is probable. Browser history and SRUM place the user at a webmail interface with outbound bytes. No artifact records a file being attached, though, and a message sent without an attachment would produce the same trace. The distinction is not stylistic. Counsel and HR act differently on the two, and mislabeling a probable finding as confirmed undermines every properly confirmed finding in the same report.

**8. Why should evidence gaps be named explicitly in a case summary rather than omitted?**

Because an unnamed gap is a hole a reviewer will find on their own, and finding it themselves is much worse for your credibility than being told. Naming gaps does three constructive things. It tells the reader exactly how far the conclusions extend, so nobody acts on a finding the evidence does not support. It converts a limitation into an action item: "the host cannot confirm webmail upload content; this requires Microsoft 365 mail-flow logs, which legal can obtain through the employee's former account or preservation request" is a next step, not a shortfall. And it demonstrates that the analysis was scoped deliberately rather than opportunistically. In the HR-WS17 case, several are worth naming. Memory is a single snapshot: the WinPmem capture at 18:01:12 UTC, shipped as three Volatility 3 plugin outputs, misses tools that had already exited, such as `7zG.exe` and `cmd.exe`. There is no NetFlow telemetry for the host, so SRUM is the only bytes-out indicator. There are no provider-side cloud audit logs. The USB device itself was never recovered, so nothing confirms what the files became after the copy.

**9. How does a case summary's structure support readers with different roles and technical backgrounds?**

The structure is layered so each reader can stop at the depth they need. The executive summary is one plain-language paragraph: what was investigated, what was found, and what is recommended. It leaves out event IDs, MFT records, and tool names, because it is what leadership will read and act on. Background and scope give counsel the provenance and boundaries they need to assess whether the work is defensible. The findings section separates confirmed from probable from gaps, which is exactly the distinction HR and legal need to calibrate action. Anyone can scan the channel analysis table. It shows both what was confirmed and what was ruled out, so the reader can see the conclusion was reached by elimination as well as confirmation. The curated timeline serves the semi-technical reader who wants the sequence. The appendices — chain of custody, tool versions and commands, the full timeline, the indicator list — carry the material a technical reviewer or opposing expert would need to reproduce the work. Nobody has to read past their depth, and nobody who needs more detail has to ask for it.

**10. What documentation should accompany the case summary as appendices, and why?**

Four, per §11.6. The chain-of-custody record, because every conclusion rests on the assertion that the evidence analyzed is the evidence collected, unaltered. Without it, the whole report is contestable regardless of its analytical quality. Tool versions and parsing commands, because forensic tools produce version-dependent output and reproducibility requires knowing exactly what was run against what. Write "MFTECmd 1.2.2.1 against `$MFT` extracted from the working copy, SHA-256 recorded," not "we parsed the MFT." The detailed timeline, so a reviewer can verify that the narrative in the body is actually derivable from the underlying entries rather than taking the summary on trust. And the indicator list — file names, SHA-256 hashes, USB vendor/product/serial, account identifiers, remote paths — because it is the operational output: the thing security uses to hunt for the same device or account elsewhere, and the thing legal uses when drafting preservation demands or discovery requests to a provider.

## Practical Exercises

**1. Run the lab simulation in `Labs/Lab11/` end-to-end on your lab VM. Capture the disk image, memory image, and artifact bundle.**

**What you should end up with:** A disk image, a memory image, and a targeted artifact bundle (registry hives, event logs, Prefetch, browser history, OneDrive databases) from a VM on which you deliberately staged a multi-channel exfiltration scenario.

**How to get there:** Follow §11.3. Create a `Confidential\` folder with test files of varying types and sizes. Sign into a personal OneDrive account and move some files into the sync folder. Connect a USB drive and copy a *different* but overlapping set of files to it. Open at least one file from each location in its native application. Optionally, send one as a webmail attachment. Optionally, delete some local copies and empty the recycle bin. Capture memory, power off, and image the disk.

**What good looks like:** You write down what you actually did — file by file, channel by channel, with times — in a sealed ground-truth note you do not consult during the investigation. That note is what makes the exercise diagnostic rather than decorative. At the end, you compare your reconstruction against it and find out what you missed and what you overclaimed. Deliberately make the channel sets *overlap but not match*: some files to USB only, some to both, some to neither. That asymmetry is the most instructive thing you can build into the scenario, and the shipped HR-WS17 data does exactly that.

**2. Hash all evidence images and record the values in a chain-of-custody log.**

**What you should end up with:** A CoC log with an entry per evidence item: description, acquisition tool and version, acquiring analyst, acquisition date and time in UTC, SHA-256, storage location, and every subsequent transfer or access.

**How to get there:** Hash immediately after acquisition, before anything else touches the file. Use `Get-FileHash -Algorithm SHA256`, or the acquisition tool's own verification output where it computes during acquisition. Record the algorithm explicitly, not just the digest.

**What good looks like:** The log records the hash *and* the time the hash was computed, and every later handling event appends a row rather than editing an existing one. Take the chapter's framing literally: this step takes 30 minutes and prevents categories of problems that surface much later, usually at the worst moment. If the images came from someone else, as in the scenario, the first log entry is your verification that the received hash matches the originally recorded value.

**3. Create working copies, verify their hashes, and structure a case folder following the conventions in earlier chapters.**

**What you should end up with:** Verified working copies of the disk and memory images with matching hashes, and a case folder following the `01_Original / 02_Working_Copy / 03_Analysis / 04_Reports` pattern.

**How to get there:** Copy, hash the copy, compare against the original's recorded digest, and log the verification. Analysis runs against `02_Working_Copy` only. `01_Original` is write-protected and untouched from this point forward.

**What good looks like:** The verification is logged as an event with a timestamp, not just noted as done. The folder structure separates evidence from derived output so that six months later it is unambiguous which files are originals, which are tool output, and which are your analysis. Parsed CSVs go in `03_Analysis`, never alongside the images.

**4. Define a specific set of at least eight investigative questions for the scenario, grouped by category.**

**What you should end up with:** A table of at least eight questions grouped by category, each with a planned evidence source and space for an answer and a confidence rating.

**How to get there:** Start from the §11.2.2 categories — Existence, Channel, USB, Cloud, Web, Email, Persistence, Cleanup — and make each one specific to your scenario. Not "was there USB activity?" but "did any removable mass-storage device connect to HR-WS17 between 2024-11-12 17:00 and 18:30 UTC, and can any of the three named pricing files be bound to it?"

**What good looks like:** Each question is answerable with a yes, a no, or a named gap, and each names its intended source before you look. Writing the source in advance is what converts the list into a collection plan. By the end of the investigation every row has an answer and a confidence rating, and the ones that came back as gaps are the content of your Limitations section. Add a ninth question that most people forget: *which of the named files went through which channels* — not whether the files moved, but the file-to-channel mapping. That is where the case is most often overclaimed.

**5. Parse the standard artifact set (MFT, USN Journal, registry hives, OneDrive databases, browser history, Prefetch, Amcache, SRUM, event logs) and produce CSV output for each.**

**What you should end up with:** One normalized CSV per artifact source in `03_Analysis`, with a parsing log recording the tool, version, exact command, input path, output path, and output hash for each.

**How to get there:** Run MFTECmd over `$MFT` and `$UsnJrnl:$J`. Run RECmd or Registry Explorer over `SYSTEM`, `NTUSER.DAT`, and `UsrClass.dat`, and SBECmd over `UsrClass.dat` for shellbags. Run LECmd and JLECmd over `Recent\` and `Recent\AutomaticDestinations\`, PECmd over `Prefetch\`, AmcacheParser over `Amcache.hve`, EvtxECmd over the event logs, and srum-dump over `SRUDB.dat`. Open the OneDrive sync-engine database and the Edge `History` file in DB Browser for SQLite. Extract text directly from `%LOCALAPPDATA%\Microsoft\OneDrive\logs\Personal\`. The shipped [`Data/HR-WS17/`](../../Data/HR-WS17/) folder is exactly this output set already produced, if you want to work the analysis without the parsing.

**What good looks like:** The parsing log exists and is complete enough that someone else could regenerate every CSV. Note the artifacts that are *absent* and why. HR-WS17 ships three Volatility 3 plugin outputs from the live WinPmem capture but not the memory image itself, and no per-host NetFlow because the endpoint was not in a monitored path. Those absences belong in the log at parse time, not discovered later when a finding needs them.

**6. Build a merged timeline across the parsed sources. Curate it down to the entries relevant to the scenario.**

**What you should end up with:** A merged CSV in the Chapter 10 schema, and a curated subset small enough to read on one screen.

**How to get there:** Normalize each source into the seven-column schema, concatenate, and sort by UTC. Then curate against the exfiltration window. In the HR-WS17 data, the window is 17:35–18:00 UTC on 2024-11-12. The curated set runs roughly: 17:38:42 `Q4_Customer_Pricing.xlsx` opened from `C:\HR\Pricing\`; 17:39:05 and 17:39:18 the two `Temp\` copies created; 17:42:08 Kingston DataTraveler 3.0 first install; 17:42:14 volume bound to `E:`; 17:43:11 and 17:43:42 shellbags into `E:\Confidential\` and `E:\Confidential\Pricing\`; 17:44:18, 17:44:55, and 17:45:32 the three USB LNK creations; 17:46:42 and 17:48:41 the two OneDrive enqueues; 17:49:18 sync window closes; 17:51:04 navigation to `outlook.live.com`; 17:55:11 `Temp\` copies deleted; 17:57:42 `C:\HR\Pricing\` deleted; 17:58:30 device removed; 18:02:14 logoff.

**What good looks like:** The curated set fits on a screen, and the earlier part of 2024-11-12 — normal Outlook, Edge, and Excel activity on local and corporate-OneDrive paths — is excluded with a stated rule rather than silently. Read the curated timeline for the shape, not just the contents: the sequence *stage locally → connect device → browse → open from device → sync to personal cloud → visit webmail → delete traces → remove device → log off for the last time* is a coherent 20-minute story, and the coherence is itself part of the finding.

**7. Investigate each plausible exfiltration channel (USB, cloud sync, webmail, email) and produce a row in a channel analysis table for each.**

**What you should end up with:** A table with one row per channel: channel, status (Confirmed / Probable / Ruled out / Not observed), the specific files involved, the supporting artifacts, and the confidence rating.

**How to get there:** Work each channel against its own artifact set. For HR-WS17 the result is:

| Channel | Status | Files | Evidence |
|---|---|---|---|
| Removable media (Kingston DataTraveler 3.0, serial `001A92053B7CBE3196B40A0F`) | Confirmed | All three pricing files | `usbstor.csv` install at 17:42:08; `mountpoints.csv` volume bound to `E:`; `shellbags.csv` navigation into `E:\Confidential\Pricing\` at 17:43:42; three LNK files with volume serial `F1D2E9A4`, label `KINGSTON`, drive type `RemovableMedia`, created 17:44:18 / 17:44:55 / 17:45:32; MFT entries for two transient `Temp\` copies |
| Personal OneDrive (`hr.user.personal@outlook.com`) | Confirmed | `Q4_Customer_Pricing.xlsx`, `Pricing_Strategy_Confidential.docx` — **not** `Margins_Q3.xlsx` | `onedrive-accounts.csv` personal account alongside the corporate one; `onedrive-syncdb.csv` two rows, `SyncState=UploadComplete`, enqueued 17:46:42 and 17:48:41, upload-completed 17:47:18 and 17:49:18, with `Sha256ContentHash` values matching `pricing-files-known-hashes.txt`; `onedrive-logs-extract.txt`; SRUM outbound bytes for `OneDrive.exe` |
| Browser webmail upload (`outlook.live.com`) | Probable | Unknown | `browser-history.csv` navigation at 17:51:04; `srum.csv` `msedge.exe` outbound bytes; no upload trace in cache or form data |
| Local email client (PST/OST) | Not observed | — | No PST/OST in the dataset. `OUTLOOK.EXE` ran from 08:48:14 for the corporate mailbox, so its store is worth parsing before you rule the channel out |
| Printing / MTP / Bluetooth / network share | Not observed | — | No supporting artifacts in scope |

**What good looks like:** The Files column is populated per channel and the entries are not identical across rows. `Margins_Q3.xlsx` has a USB LNK at 17:45:32 but no row in `onedrive-syncdb.csv` — it went to the USB device and nowhere else. Getting that right is the difference between a defensible report and an overclaim. Note also the strongest single piece of evidence in the whole case: the `Sha256ContentHash` values in the sync database match the hashes legal provided, which binds the uploaded blobs to the specific documents rather than merely to files of the same name.

**8. Identify cleanup activity in your lab data, document what was cleaned up, and identify which artifacts still preserve the evidence.**

**What you should end up with:** A table of cleanup events: what was removed, when, the artifact that records the removal, and what still survives that the cleanup did not reach.

**How to get there:** Focus on the USN Journal, which retains deletion records after the files are gone. In HR-WS17, the two transient `Temp\` copies were deleted at 17:55:11 (`usn-journal.csv`), and `C:\HR\Pricing\` itself was deleted at 17:57:42 (`usn-journal.csv`, `mft.csv`). Then enumerate what survived. The LNK files in `Recent\` still name the deleted local paths and the USB paths. The shellbags still record the `E:\Confidential\Pricing\` navigation, and the jump lists still carry the MRU entries. The registry still holds the device and account records, and the OneDrive sync database still holds the upload rows.

**What good looks like:** The table makes the asymmetry visible. The user removed the files but not the metadata about them. That is the normal outcome, because the metadata lives in a dozen places most people do not know exist. Include the interpretation: deleting the source directory minutes before a final logoff on the last day of employment is behavior, and behavior is evidence. Be careful with the limits, though. Deletion establishes that files were removed, not that the removal was intended to defeat an investigation, and the summary should say so.

**9. Write a one-page case summary using the template in 11.6, with at least three confirmed findings and one named evidence gap.**

**What you should end up with:** A one-page document following the §11.6 structure: header block with case reference, author, date, audience, and distribution restriction; executive summary; background; scope and methodology; findings split into confirmed, probable, and gaps; channel analysis table; curated timeline; recommendations with rationale; limitations; appendix list.

**How to get there:** Lead with the conclusion. A workable executive summary for HR-WS17: *Analysis of the preserved workstation HR-WS17 confirms that three confidential pricing documents were copied to a personally owned USB device on 12 November 2024, and that two of the three were additionally uploaded to a personal cloud storage account the same afternoon. The activity occurred in a 20-minute window immediately before the employee's final logoff. Local copies of the files and the folder that contained them were deleted shortly afterward. A probable third channel — a personal webmail session — is consistent with the evidence but cannot be confirmed from the workstation alone.* Then support it with three confirmed findings: the USB channel with device identity, the OneDrive channel with hash-verified file identity, and the cleanup activity. Add the probable webmail finding with its inferential step named, and the gaps.

**What good looks like:** Confirmed and probable are visibly separated, and the probable finding states what would elevate it. The recommendations carry a "because" — *request Microsoft 365 mail-flow and audit logs for the employee's personal account through counsel, because the host cannot resolve whether the webmail session included an attachment*; *issue a preservation and return demand for the Kingston DataTraveler, serial `001A92053B7CBE3196B40A0F`, because the device is the only source that can establish what happened to the files after the copy*; *treat all three documents as compromised for customer-notification purposes, because two channels are confirmed and both are outside organizational control*. The executive summary contains no event IDs, no artifact names, and no tool names.

**10. Review your summary as if you were the recipient: would a legal reviewer with no forensic background be able to understand and act on it? Revise as needed.**

**What you should end up with:** A revised summary plus a short note listing what you changed and why.

**How to get there:** Read it in the voice of each audience. As counsel: can I tell what is provable, what is inferred, and what is unknown? Is there anything here that an opposing expert could characterize as overstated? As HR: does this support a specific action against a specific person, and is the account attribution clear? As leadership: do I know in one paragraph what happened and what I am being asked to approve? Then hunt for three specific defects: jargon that survived into the executive summary, findings whose confidence label does not match the evidence behind them, and any sentence that asserts intent rather than action.

**What good looks like:** The revision log names concrete changes: a claim downgraded from confirmed to probable, a sentence about the user "attempting to conceal" rewritten as "deleted the source directory at 17:57:42," a jargon term replaced. The most valuable check on this material is the file-to-channel mapping. Go back and confirm that every sentence naming a file also names the correct channel for that file, and that no sentence implies all three documents crossed all channels. The moment your summary says "the pricing files were uploaded to a personal cloud account" without qualification, you have overclaimed, because only two of the three were.

## Common mistakes on this chapter

- **The multi-channel overclaim.** This is the canonical failure on the capstone, stated here in the specific form the data produces. HR-WS17 has three named pricing files. All three were copied to the USB device. `lnk-files.csv` has three LNKs carrying volume serial `F1D2E9A4`, label `KINGSTON`, drive type `RemovableMedia`, created at 17:44:18, 17:44:55, and 17:45:32. Only two reached the personal OneDrive account: `onedrive-syncdb.csv` contains exactly two rows, for `Q4_Customer_Pricing.xlsx` and `Pricing_Strategy_Confidential.docx`. `Margins_Q3.xlsx` went USB-only. Writing "the three pricing files were exfiltrated via USB and personal OneDrive" collapses a precise finding into a false one. Once a reviewer finds that kind of error, it casts doubt on every other claim in the report. Build the file-to-channel mapping explicitly as a table and check every narrative sentence against it.

- **Answering "what happened on the host?" instead of "where did the data go?"** The chapter's field note describes exactly this: four hours spent on an exhaustive super-timeline that could not answer counsel's question, because the exfiltration channel was one the responder never instrumented. Host timelining is a supporting technique, not a search strategy. Enumerate the plausible channels first, let that enumeration drive collection, and build the timeline to support the channel answers. An investigation that opens the image before asking "what are all the ways data could leave this host?" is running in the wrong order.

- **Reporting the webmail channel as confirmed.** Browser history shows the personal mailbox at 17:51:04, a compose page at 17:52:11, and Sent Items at 17:54:42, and SRUM shows `msedge.exe` outbound bytes. That sequence points to a message being sent, not just mail being read. No host artifact records a file being attached. The correct label is Probable, with the inferential step named and the elevating evidence identified: provider-side Microsoft 365 mail-flow and audit logs. Overclaiming on the weakest channel is the fastest way to weaken the two channels that are genuinely airtight.

- **Treating deletion as an evidentiary gap rather than an observation.** New responders often report the deleted `C:\HR\Pricing\` directory as something the investigation lost. It is something the investigation found. The USN Journal records the deletion at 17:57:42 with a timestamp more precise than most of the surrounding evidence. The LNK files, jump lists, shellbags, and registry entries that reference the deleted paths all survived. Cleanup activity is its own finding, and the surviving-metadata inventory is what demonstrates the deletion did not succeed at its apparent purpose.

- **Inferring intent from artifacts.** Forensic artifacts record actions, never motives. The evidence establishes that files were copied to a device, uploaded to a personal account, and then deleted locally, all within one session on the employee's last day. It does not establish that the employee intended to harm the organization, knew the material was confidential, or lacked authorization. Those are determinations for HR, counsel, and the employment record, informed by policy and by the employee's role. Write actions with timestamps and sources. Leave "attempted to conceal," "stole," and "deliberately" out of the findings. This is a discipline issue, not a politeness one: intent language is the first thing an opposing expert attacks, and it is unnecessary because the action sequence is damning enough on its own.

- **Skipping the hash comparison because the file names match.** The names in the sync database, the LNK targets, and legal's reference list are all the same, which makes it tempting to treat identity as settled. It is not. File names are trivially reusable, and a `Q4_Customer_Pricing.xlsx` in a personal OneDrive folder could be an unrelated or modified document. The `Sha256ContentHash` column in `onedrive-syncdb.csv` matches the digests in `pricing-files-known-hashes.txt` exactly, and stating that match explicitly is the single strongest sentence available in the report. Note also what the hash comparison cannot do: the USB channel has no content hash available from host artifacts at all, so its file identity rests on name, size, and path. That basis is weaker, and worth saying so.

- **Writing a summary that only a forensic analyst can read.** The case summary is usually the only document non-technical stakeholders read in full, and it is the basis for decisions about legal action, regulatory disclosure, and customer notification. An executive summary containing "USN Journal," "shellbag," "EID 4634," or "MFT `$STANDARD_INFORMATION`" has failed its audience regardless of how correct it is. Move that material to the body and appendices, and write the top paragraph so that someone with no forensic background finishes it knowing what happened and what they are being asked to decide.
